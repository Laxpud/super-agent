## 已补入的首版要求

[本地工作区执行](requirements/v1-scope.md#5-本地工作区执行与-v1-权限边界)原先只有角色职责与通用能力描述，没有把本地读取、搜索、修改和运行检查定为首版底线。当时补充了本地工作区关联、任务级指定与授权的区别，并要求实际操作、可核对结果和越界拒绝。当时的 Studio 工具注册（`src/managed-worker/index.ts:374–411`）仍只有文字、协调与受管文档路径，不能把上述验收记为通过。

## 候选缺口

### 1. 从统一入口把工作交给已存在的项目

- **需求缺到哪一层：**旧基线已有跨渠道接续原则和“项目由现任 Leader 组织”的要求，也明确不镜像 Leader 和 Worker 的内部对话，但此前没明确验收“在 Assistant 对话里指名现有项目交办”这一日常动作。现已统一纳入 [V1 跨入口指名项目交办](requirements/v1-scope.md#43-跨入口指名项目交办)。
- **现状：**Web 通过项目选择器切换对话（`src/studio-web/studio.tsx:79–89`），已选中项目才会按会话地址找现任 Leader（`src/studio/sessions.ts:239–247`）。飞书普通来信固定进入 Assistant（`src/studio/service.ts:256–291`），Assistant 能查项目、提议立项、派文字任务，但角色工具没有把原请求送给既有项目 Leader 的入口（`src/managed-worker/index.ts:385–391`）。个别文档控制路径不等于通用项目分流。
- **建议最低验收：**在飞书明确指向一个已存在的项目，现任 Leader 安排工作；请求、状态及适合原入口查看的结果可追踪，不广播内部对话。无法唯一确定项目时才澄清，不重复建项目或任务。

### 2. 用户能查从交办到交付的任务状态

- **需求缺到哪一层：**旧基线规定了「待我处理」和汇报原则，但没有单独指定用户怎样查找所有已交办工作，以及消息处理、任务执行、交付三个状态怎样区分。现已纳入 [V1 统一任务视图与「待我处理」](requirements/v1-scope.md#62-统一任务视图与待我处理)。
- **现状：**Studio 对外操作（`src/studio/protocol.ts:98–111`）提供对话、待办和会话记录，没有统一的任务列表或任务详情；已有项目工作命令（`src/managed-worker/project.ts:543–576`）和Assistant 实时工作查询（`src/studio/sessions.ts:190–197`），但分散。后台任务一经接手，原消息轮次就可标记为 `completed`（`src/studio/sessions.ts:357–367`），界面显示为「已完成」（`src/studio-web/locales.ts:83`），但这不表示任务已交付。恢复时，排队和运行中的消息都标为中断（`src/studio/store.ts:480–492`），不自动重跑。
- **建议最低验收：**刷新页面、换入口或重启后，不记底层 Session ID 也能找到同一任务，分别看见未开始、在执行、等确认、受阻、中断或已交付，以及原请求、负责人、结果与适用的下一步。任务视图不应把正常运行事项计入「待我处理」。

### 3. 用户给任务提交实际材料

- **需求缺到哪一层：**旧基线只覆盖了历史资料迁移与纯文字同步，没有指定非纯文本的任务材料入口。现已归入 [V2 文件材料输入与受管产物交付](requirements/roadmap-and-blueprint.md#31-文件材料输入与受管产物交付)。
- **现状：**Studio Web 发消息只接受正文、回复与引用（`src/studio/http.ts:16–30`），飞书入口只收 `text`（`src/studio/feishu.ts:20–33`），也没有把附件或受支持的文件引用作为任务材料交给 Worker 的通用路径。引用聊天文本和选择工作区都不能替代显式提交任务材料。
- **建议最低验收：**为一个任务附一份支持的材料（如 Web 上传一份表格或给出可读取的文件引用），只交给获准的执行者。打不开、不支持或需要另一入口时给出明确反馈，不当作已读取，也不要求用户把整个材料粘成文字。

### 4. 交付能取回的非文字成果

- **需求缺到哪一层：**旧基线要求成果可访问、不因临时目录清理丢失，但未定义文件型交付与取回边界。现已归入 [V2 文件材料输入与受管产物交付](requirements/roadmap-and-blueprint.md#31-文件材料输入与受管产物交付)。
- **现状：**Studio 成果协议（`src/studio/protocol.ts:14–34`）只有标题、文本和 Session 来源，Web 展开文本和来源（`src/studio-web/conversation.tsx:65–71`），飞书发送同步文本或确认卡片（`src/studio/feishu.ts:297–324`）。可以回传一段文字或人工填的链接，但没有受管文件成果和取回操作。
- **建议最低验收：**Worker 生成一份文件（如表格、图或补丁），任务关联实际产物；Worker 退出后仍能从原任务或另一入口定位并通过获准途径取回。不能直接在飞书提供时说明取得方式，不用本机临时路径冒充可用交付，也不默认外传。

### 5. 项目不是只增不减的对话列表

- **需求缺到哪一层：**旧基线未定义如何变更项目目标、结束/归档或恢复项目。现已纳入 [V1 项目生命周期](requirements/v1-scope.md#61-项目生命周期)。
- **现状：**项目表（`src/managed-worker/project-store.ts:122–134`）没有生命周期状态；现有建项和移交路径（`src/managed-worker/project-store.ts:537–584`）写入初始目标或更新管理轮次，没有更新项目目标或结项的操作。项目档案命令（`src/managed-worker/project-archive.ts:26–66`）管理事实摘录，不是关闭项目。
- **建议最低验收：**更正项目目标不必另建项目；显式结束后停止按该项目承接新工作，既有成果可查，在途工作和已发出的外部动作按实际状态另行处理。恢复不自动重启旧任务或复用失效授权。

### 6. 飞书发出、Studio 受理和执行是不同的状态

- **需求缺到哪一层：**旧基线承认手机发送不等于宿主收到，但未指定如何核对原消息受理状态及安全补交。现已纳入 [V1 Web 与飞书互通](requirements/v1-scope.md#42-web-与飞书互通)。
- **现状：**飞书入站（`src/studio/feishu.ts:214–251`）依赖长连接；无法确认登记时记宿主告警。使用指南（`docs/customization/agent-studio.md:45–54`）明确不补捞断线历史。已登记任务有派工回执，出站也区分是否确认，但普通来信没有一条普遍可查的受理回执；未匹配到已有话题的来信还可能不登记（`src/studio/service.ts:256–280`）。
- **建议最低验收：**用户能区分一条原消息是否已登记、任务是否已受理执行、是执行结束还是回传未确认；重新提交前能核对或明确确认要补交，重复、旧消息不自动变成新任务。对未受理的重要更正，也不能报为已生效。

## 不归为「没写」的项目

- 与 Worker 在原任务下直接交流、更正撤销后终止旧授权、动作级安全约束、共享资源并发冲突已在[V1 规格](requirements/v1-scope.md)与[终态蓝图](requirements/roadmap-and-blueprint.md)中按阶段分流落地。
- 项目档案与跨项目经验维护、精细模型调度、Watchdog 主动巡查与恢复均已分阶段归入[终态蓝图与演进路线](requirements/roadmap-and-blueprint.md)。
- 微信里接单、群聊协作、每种 Worker 一个永久 Bot、为每个动作重复人工审批、建设新的远端执行后端，以及自动同步所有原始文件，没有必要作为本次「基础缺口」补进来。

## 建议顺序

1. 用一条真实本地任务验收已补入的要求：指名项目或目录 → 定向派工 → 实际读取或修改及检查 → 回到原请求并可查询。先核实宿主能限制实际文件目标和命令副作用，不能只挂普通工具或设置工作目录。
2. 让用户能查这条任务和实际结果，再补最小材料输入与文件交付，形成不依赖全文粘贴的流程。
3. 敲定项目日常管理和断线受理、补交的行为，再扩展到更多任务类别、资料类型和执行环境。

只有本地工作区执行已写入需求；其他候选留待确认。
