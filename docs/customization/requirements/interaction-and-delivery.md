## 交互、渠道与自主性

### 指令来源与入口

当前只有用户本人可以下达指令。采用常规身份白名单即可，群聊协作和复杂群组权限模式不属于当前需求。

用户可以通过 Assistant 交代工作，也可以进入任务，直接与 Leader 或 Worker 讨论细节。直接交流仍属于原任务，不会悄悄改变负责人或汇报关系。重要的范围变化和项目决定应让相关负责人可查，不能只留在孤立的聊天中。

首版以 DSH GUI 和飞书为主要入口。微信是后续扩展目标，不是首版前提。渠道应可扩展，不能每个渠道各自形成一套互不相干的工作室。

用户的私聊入口共享任务连续性：可以在一个入口发起任务，在另一个入口追问或调整。这不等于把所有聊天拼成一个上下文、广播所有消息，或将私人上下文带入未来的群聊。当前不要求群聊；以后引入时，也只共享明确放进去的任务和信息。

跨渠道说“继续那个任务”时，能够唯一定位就接续该任务；存在多个合理候选，且选择会影响实质动作时，才询问任务归属。不能因为入口改变就新建一份重复任务。

同一条用户消息重复投递时，不重复创建工作，也不将其当作新增授权。已知较早的指令不能仅因迟到，就覆盖已经确认的较新更正；跨渠道先后关系确实无法判断，且会影响实质动作时，应澄清受影响的决定。具体登记顺序、来源消息识别与冲突处理留给技术设计，不预设复杂的跨渠道时钟系统。

### 更正、撤销与暂停

用户直接向 Assistant、Leader 或 Worker 发出的有效指令，效力不取决于负责人是否已经阅读或再次批准。系统应及时将重要变化登记为当前任务依据，并让相关负责人可查；“可查”不能代替执行前实际采用新要求。

渠道收到消息与任务控制状态登记生效应明确区分。只有相应任务依据和执行约束已经更新，才能向用户确认暂停、停止或范围调整已生效；不能仅把消息放进 Worker 聊天历史，等待模型读到后才阻止旧动作。

- 停止、撤销或范围缩小登记生效后，受影响的待执行动作不得按旧范围启动，相关旧批准失效。不需要等待 Leader 或 Worker 阅读，也不需要 Leader 再批准用户的更正。
- 工作室侧动作启动或外部调用发出前，核对当前有效授权和约束。已经在工作室内部排队、已经派工或曾经获批，都不是继续使用旧授权的理由。
- 对已经开始的动作或已经发出的外部调用，按当前指令和工具能力处理，并如实说明已发生的效果、能否中止和仍不确定的部分，不能声称尚未发生或保证可以撤回。
- “暂停后续工作”与“取消或终止已提交的外部作业”分别记录和处理，不能自行将两者等同。后续处理被暂停时，仍可记录外部作业状态，但不能因完成或额度恢复事件自动启动后续业务；取消或终止外部作业仍须符合用户指令和动作授权。

### 自主性

在已交代的工作范围内，负责人应主动推进必要且已授权的步骤。已明确授权的持续目标或维护范围，可以持续推进，不必每个子步骤重新请求一次。

对于范围外的新工作，系统可以提出建议，但不能仅因某个 Bot 发现机会就自行开工。外部文档、工具结果和其他参与者可以提供证据，不能成为新增人类授权。

确实缺少业务决定时可以澄清，但不能把已经授权的动作重新包装成审批问题。

### 汇报与交付

默认简洁汇报，必要时展开细节。报告有意义的进展、最终结果和实质性障碍，不反复报告正常作业“仍在运行”。

交付应说明完成了什么、依据是什么、还有什么未完成或不确定。工具返回成功、代码已写出、作业已提交，都不等于任务完成。交付也不统一要求是 Pull Request 或对外发布。

交付应提供用户可访问、后续可重新定位的成果入口。当前渠道无法直接呈现或传输时，应说明可用的取得方式，不能只给用户无法访问的临时路径。需要保留的成果，不应因临时会话结束或工作目录清理而意外丢失；切换入口后应能找回已有成果。不同类型的成果可以采用不同取得方式，不预设统一云盘，也不要求所有渠道传输全部文件。

简单任务可以只委派一个 Worker，并在原入口直接展示其结果，保留任务归属和交付来源。不要求为转述同一份答案再调用一次 Assistant。
