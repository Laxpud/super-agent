## 目标与范围

Agent Studio 是在上游研究原型基础上定制的、供用户个人使用的通用 AI 工作室。工作可以包括开发、科研、技术或论文写作、系统维护等。这些类别不是固定部门，也不与某个 Bot 或模型永久一一对应。

用户应当能够自然地交代工作，复用合适的 Bot 及其经验，让已授权工作自主推进，而不必反复说明上下文，或重复批准原指令已经覆盖的动作。系统应减少不必要的人类注意力消耗，同时保持责任明确、报告诚实和用户对工作范围的控制。

定制后的系统不局限于单个代码仓库。GitHub 仓库、Pull Request 或对外发布，不是所有任务的前提或统一交付形式。上游已有概念和集成是可以改造复用的实现基础，不应成为限制个人工作范围的产品约束。

首版只有用户本人能够下达指令，不建设群聊协作产品。本次定制不建设、部署或管理本地、SSH、cx05、Slurm 等执行后端，也不承诺接入新的远端执行环境。让 Worker 通过 Harness 已有的本地执行能力操作获准的工作区、接入宿主侧动作拦截与沙箱，以及[协调长作业的生命周期与任务接续](jobs-and-oversight.md#长作业协调)，属于本次定制范围；复用已有执行基础设施，不等于可以忽略这些运行时改造。

## 概念与身份

| 概念 | 在本次定制中的含义 |
| --- | --- |
| 角色 | 职责和权限边界，例如 Assistant、Leader、Worker。角色不是模型名称。 |
| Bot | 具有稳定身份的工作主体，拥有设定、合作偏好、积累的经验和过往工作引用。一个 Bot 可以有多个工作会话。 |
| 模型配置 | 某次使用所选择的 provider、模型及其支持的思考深度。它提供推理能力，不拥有 Bot 的身份或记忆。 |
| Session／会话 | 某一段工作的交互与执行上下文。新建会话不等于新建 Bot。 |
| 任务 | 一项有范围、负责人和预期结果的已请求或已授权工作。 |
| 项目 | 由用户明确立项的持续性工作，具有负责的 Leader 和持续维护的项目记录。不等同于仓库、目录或会话。 |
| 项目档案 | 项目目标、范围、决定、事实、成果、当前进展、已知问题及后续事项的记录。维护期间仍然有效，不是只有结项后才存在的归档材料。 |
| 长作业 | 运行时间超过一个 Agent 活动轮次的操作或外部过程。其执行生命周期与任务、会话分开。 |

Assistant 和 Leader 采用同一种 Bot 抽象，但不是合并成同一个 Bot 实例。Assistant 是面向用户的角色名，Router 是其内部架构名称。**Assistant 就是 Router，不是两个主体，也不是两层审批。**不再使用 Chief 作为该角色的名称。

更换 Bot 的模型，不等于创建新 Bot、更换项目负责人或丢弃记忆。新建或恢复会话，也应保留 Bot 身份。真正的负责人更换，是将项目从一个 Bot 交给另一个 Bot，而不是仅仅选择另一种模型。

系统应按需向选定模型提供持久化状态。这不保证不同模型表现完全一致，也不意味着积累经验会训练或改变底层模型权重。

## 角色与职责

### Assistant／Router

Assistant 是默认入口，但不是唯一入口。它理解和澄清要求、路由工作、安排合适的参与者、掌握整体状态，并向用户传达有价值的结果。

Assistant 不亲自执行业务或技术任务，包括简单任务。理解要求和路由工作需要必要的业务理解，但不因此获得自行完成分析、写作、实现或提出新技术结论的职责。不能因为它是统一入口，就让它接管项目内部的技术管理。

这项分工分为可由宿主强制执行的权限边界，以及需要通过行为验收约束的输出边界：

| 边界 | 约束方式 |
| --- | --- |
| 不运行业务命令、修改业务文件或调用业务 API | 由 Harness 的角色工具权限和宿主执行边界强制约束，不能只依赖提示词。 |
| 不自行完成应交给 Worker 的分析、写作和实现，包括无须工具的任务 | 通过角色提示词、交付来源、消息流程和行为验收约束；不能宣称仅靠工具权限即可保证。 |
| 理解和澄清要求、路由、查看状态、转达或概述已有成果 | 属于 Assistant 职责；需要新增技术判断或业务内容时，按既定角色职责安排 Worker 或 Advisor；项目内工作仍由 Leader 组织。 |

Assistant 展示的业务交付、咨询意见和项目汇总，应能追溯到实际承担相应职责的主体及其结果，包括 Worker 的执行成果、Advisor 的咨询意见，以及 Leader 的检查与整合。Assistant 可以转达或概述已有成果，但不能自行补充新的技术结论，也不能伪造或改变成果来源。

对于未立项工作，Assistant 安排 Worker，并作为 Worker 的直接负责人，负责任务安排、依赖协调和交付组织。需要技术整合或必要检查时，应明确指定承担这项任务的 Worker；可以由已经参与任务的合适 Worker 兼任，不必另建“整合 Worker”。需要专家判断时，可以安排 Advisor 提供分析。整合 Worker 不获得给其他 Worker 派工的权限，这种安排也不自动形成项目或持久 Leader。

对于已立项项目，除非用户指定负责人，否则由 Assistant 安排或选择 Leader。可以复用已有合适 Bot；新项目不必自动新建 Bot，也不必预先创建完整团队。

Assistant 可以建议立项，但不能把自己的建议当成用户已经作出的立项决定。

### Leader

每个明确立项的项目都有且只有一个当前负责的 Leader，不允许多个 Leader 同时管理同一个项目。同一个 Leader Bot 可以同时负责多个项目，也可以积累经验并在之后继续负责其他项目，不与单个项目永久绑定。各项目仍保持分开的工作上下文。

Leader 维护项目目标和范围，组织任务及依赖关系，分配 Worker，整合成果、识别遗漏并报告整体进展。其责任跨越阶段、会话和维护工作，不随一次派工结束而消失。

Leader 应尽量不亲自承担技术执行。这是通过系统提示词引导的分工要求，不通过工具权限禁止 Leader 进行技术执行。它需要理解必要背景，以组织工作和判断成果是否解决问题，但不能因为任务困难，就把自己变成最强的执行 Worker。

Worker 遇到困难时，Leader 可以识别障碍类型、调整任务或补充信息、咨询 Advisor，或选择更合适的执行模型和思考深度。这些手段互补，不规定统一的先后顺序：

- 方向不清、存在争议或难以判断时，可以咨询 Advisor。
- 方向明确而执行能力不足时，可以调整 Worker 的模型配置。
- 信息缺失或任务拆分不当，不一定要靠更昂贵的模型解决。
- 咨询 Advisor 不替代执行；升级执行模型，也不能排除本来需要的咨询。

**Leader 在共同配置范围内，直接分配项目内 Worker 并选择其模型配置，不需要请求 Assistant／Router 代办、批准或转述每次交流。**

### Worker

Worker 承担已分配的调查、实现、分析、写作等实际执行工作。“更强的 Worker”通常表示选择能力更合适的执行配置，不意味着新增组织级别，也不必创建新的永久 Bot。

Worker 向该任务的直属 Leader 汇报；任务没有 Leader 时，向 Assistant 汇报。Worker 之间不自行发起横向沟通、协调或派工，也不能通过共享记录间接要求其他 Worker 执行或改变共同约定。读取负责人指定的共享事实和其他 Worker 的成果，不属于横向派工，具体边界见[归属与读取](memory-and-records.md#归属与读取)。Worker 不能创建子 Worker 或继续向下派工；需要拆分或补充工作时，向负责人提出建议。

Worker 的执行受用户任务和授权范围约束。完成调查，不等于获准继续实现、安装、发布或自行立项。

不要求所有 Worker 都拥有永久 Bot 身份。有实际复用价值时，可以保留专业执行 Bot；首版不要求建立完整的永久员工花名册。

#### 本地工作区执行

首版必须能让 Worker 在获准的本地工作区实际执行任务。GUI 和飞书都能发起；未立项的任务由 Assistant 路由，已立项的由 Leader 组织。按任务选择所需的执行能力和权限，不把 Worker 固定成文本、文档或代码等角色。纯文本委派和受管文档写入仍可用于各自适合的任务，但不能替代本地执行。

- **只读调查。** Worker 能自行列目录、搜索和读取授权范围内的文件，并以实际读取到的文件路径和位置作为结论依据。用户不必先把目录结构或源码贴到聊天里。
- **修改与检查。** 用户明确授权后，Worker 能修改指定范围内的本地文件，并运行任务所需且副作用可约束的现有本地检查。交付能核对实际改动和检查结果；未执行、失败或结果不确定时明确说明，不把草稿或计划当作已经完成的操作。
- **执行边界。** 派工必须确定[本次工作区](project-lifecycle.md)及允许的操作，由宿主限制实际目标和副作用，不能只设工作目录或依靠提示词。只读任务不能写入；给出路径或关联项目不自动授予读写、运行命令、提交、发布或外发文件的权限。已有明确授权且可约束的操作不逐条要求用户确认。更正、暂停或撤销后，受影响动作不得继续使用旧批准，按[动作授权与执行约束](action-authorization.md#依据与作用范围)核对现行范围。

### Advisor

Advisor 针对方向不明、争议和困难问题提供专家分析。Leader 可以直接咨询 Advisor，不需要 Assistant 协调或转述。未立项工作由 Assistant 安排所需咨询，不因此新增 Leader。咨询按需围绕明确问题发起，不是所有困难任务的强制前置步骤，也不要求为复述同一意见额外调用 Worker。

Advisor 提供判断和建议，Worker 承担执行。同一个模型可以用于这两种角色，但不能因此混淆职责。更强的执行模型也不是只能用于 Advisor。

### Guard

Guard 依据用户已有指令，代用户对待执行动作作出授权判断。它不是交付质量 Reviewer，也不是把常规审批请求转交给用户的中转。具体要求见[代用户进行动作授权](action-authorization.md#代用户进行动作授权)。

### Watchdog

Watchdog 独立检查服务健康、任务进展、停滞和可能的目标偏离，并在授权范围内协助报告或恢复问题。它不是第二个项目经理，也不是替代技术负责人。具体要求见[监督与故障通知](jobs-and-oversight.md#监督与故障通知)。

### 暂缓的角色

暂不设置独立的交付 Reviewer。Leader 对成果进行检查和整合，是负责人的正常职责，不能以此变相恢复独立 Reviewer 角色。

每一种职责都不必对应一个独立常驻服务、持续运行的模型会话、独立公开聊天账号或人格。各角色可以共用调用和任务机制，按职责配置权限、输入和输出。不新增长作业角色或维护角色。
