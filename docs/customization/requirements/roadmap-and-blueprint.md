# Agent Studio 终态蓝图与演进路线

> **更新日期：** 2026-11-27　｜　**定位：** 沉淀 Agent Studio 的长期架构构想与分阶段演进路线，确保 V1 演进不偏航、不把未来堵死，同时不将终态能力强塞进 V1。

## 1. 长期核心概念模型

Agent Studio 的长期设计围绕以下七个相互解耦的概念展开：

| 概念 | 含义与解耦边界 |
| --- | --- |
| **角色（Role）** | 职责与权限边界（Assistant、Leader、Worker、Advisor、Guard、Watchdog），不是模型名，也不要求一一对应常驻服务或独立账号。 |
| **Bot** | 具有稳定身份的工作主体，承载长期设定、合作习惯、跨项目经验与过往工作引用。一个 Bot 可拥有多个工作会话。 |
| **模型配置（Model Profile）** | 某次调用使用的 provider、模型与思考深度组合。更换模型不等于新建 Bot、更换负责人或丢失记忆。 |
| **会话（Session）** | 某一段交互或执行上下文。新建、切换或压缩会话不改变 Bot 身份，也不打断项目或长作业归属。 |
| **任务（Task）** | 有明确范围、负责人、授权边界与预期交付的工作单元。 |
| **项目（Project）** | 经用户明确立项的持续性工作，拥有唯一当前 Leader 与持续维护的项目档案；不等同于单个仓库、目录或会话。 |
| **长作业（Long-running Job）** | 运行时间跨越单个 Agent 活动轮次的外部进程或计算任务，其生命周期与会话、任务解耦。 |

核心不变式：
- **跨项目经验跟 Bot 走，项目事实跟项目档案走**：同一个 Leader Bot 可以在项目 B 复用项目 A 积累的方法经验，但不能悄悄带入项目 A 的事实假设或授权。
- **管理权与执行权唯一且可追溯**：同一项目只有一个当前生效的 Leader；移交或轮次替换后，旧实例不能继续派工或推进同一执行步骤。

## 2. 分阶段演进路线

| 阶段 | 主题 | 核心能力 |
| --- | --- | --- |
| **V1（当前）** | 可用闭环与自举 | 统一入口（Web + 飞书）、务实角色分工、本地工作区真实执行与分级权限拦截、统一任务视图与项目生命周期、基础档案与偏好、自举迭代与无缝更新。详见 [V1 规格与验收](v1-scope.md)。 |
| **V2** | 日常增效与智能守卫 | 文件材料输入与受管产物交付、模型语义 Guard 与有限纠错复核、精细模型调度与 Advisor 协作、多任务共享资源并发隔离与合并。 |
| **V3** | 自治长作业、韧性与长期记忆 | 通用外部长作业跨重启观测与自动接续、共享额度池停池与无模型故障通知、Watchdog 独立监督、五层记忆与遗忘失效传播、更多私聊渠道扩展（如微信）。 |

## 3. V2 规划：日常增效与智能守卫

### 3.1 文件材料输入与受管产物交付
- **材料输入**：Web（及后续支持的渠道）允许用户直接为任务附加本地文件或受支持的文件引用（表格、论文、日志、配置文件等），定向交给获准执行者，告别全文粘贴。不支持或不可读时明确反馈，不假装已读取。
- **受管产物交付**：Worker 生成的非文本成果（图表、表格、补丁包、分析报告等）关联为任务的受管产物，具备稳定标识与跨端可取回入口，不因 Worker 会话结束或临时目录清理而丢失；飞书无法直接传输时给出明确取得方式，不默认外传。

### 3.2 模型语义 Guard（代用户做动作授权）
在 V1 的沙箱与分级权限基础上，引入类似 Codex Guardian 的动作级语义审查，进一步降低人类审批打扰：
- **判断逻辑**：基于真实用户原始指令、跨渠道补充与最新撤销记录（Worker 自述和摘要不可冒充用户授权），判断具体待执行动作的实际效果是否落入已授权范围。例如用户授权“清理选中的算例结果、保留输入文件”，Guard 补查上下文后直接放行合规删除，拦截对其他算例或输入文件的操作。
- **确定性与成本控制**：明确允许的常规操作仍走确定性放行，不每次工具调用都调审批模型；仅在需要语义判断实际效果时启用模型审查。
- **拒绝与有限纠错复核**：Guard 明确拒绝后，禁止靠改写命令或换包装脚本反复试探；仅在出现新证据、实质缩小范围，或执行方具体指出事实读取/规则适用矛盾时，允许有记录、有次数上限的纠错复核。复核期间仍禁止执行，动作或授权版本变化则旧批准立即失效。
- **硬前提**：模型审批永远不替代底层沙箱，也不放宽角色职责边界。

### 3.3 精细模型调度与 Advisor 协作
- **调度偏好与角色边界**：支持默认优先级 **效果 → 费用 → 速度**（先满足任务必需能力，再比较费用和速度，不默认一律拉满最高档）；用户可按“provider + 模型 + 思考深度”配置允许清单、各角色默认值与能力上下限。
- **Advisor 按需咨询**：方向不明、存在争议或复杂疑难时，Leader（或未立项时的 Assistant）可直接咨询 Advisor 获取独立专家建议，不替代执行。保留用户此前表达的参考偏好与限制记录（如 Advisor 倾向高思考深度强推理配置，且部分模型按用户配置限制用途，具体可用列表以当前环境配置为准）。
- **反复失败止损**：同一任务反复失败且拿不出新证据、可检验假设或实质性策略变化时，当前负责人停止空转，保存已有进展并标为 `blocked`，报告具体障碍与继续条件。

### 3.4 共享资源并发修改保护
- 当多个任务并行修改同一本地仓库或共享资源，或任务执行期间用户手动修改了同一文件时，通过工作区隔离（如独立分支 / git worktree）、版本基线比对或串行提交机制识别冲突；兼容修改安全合并，无法安全合并时明确报告冲突，绝不静默覆盖。

## 4. V3 规划：长作业、韧性与长期记忆

### 4.1 通用外部长作业协调
面向科研仿真（如工作站脚本、SSH / cx05 / Star-CCM+）、模型训练、批量编译等运行超过单轮会话时限的外部作业：
- **适配前提**：不自建计算调度器或执行后端；适用于现有工具能提供稳定作业引用、状态查询、结果/日志入口或完成信号的外部作业。缺少观测能力时如实标明不可自动观测，不盲目重提交。
- **生命周期解耦与槽位释放**：外部系统接受作业后，作业独立存活——Worker 等待、会话结束、额度耗尽或 Studio 正常重启均不得清理终止外部作业；等待期间释放 Agent 执行槽位，不维持空转推理循环。
- **低成本观测与安全接续**：优先使用程序低成本检查或事件信号；作业状态暂时不可查时视为“未知”而非“失败”，绝不因此重复提交。作业完成后，核对当前负责人、人工暂停状态与现行授权，按需唤醒负责人携带变化摘要进行后处理；外部作业的“暂停后续处理”与“取消外部作业”严格区分。

### 4.2 共享额度池停池与无模型故障通知
- **共享额度池保护**：配置共用同一推理额度池的 provider 映射；准确区分临时限流与明确额度耗尽。一旦确认耗尽，立即停止受影响池子的业务调度和底层自动重试，保留持久化进展，且不终止已提交的外部长作业。
- **不依赖耗尽模型的通知**：即使 Assistant 与 Worker 共用同一个耗尽的额度池，宿主/监督程序仍直接通过已配置渠道（Web / 飞书）发送明确标明来源（如“系统通知 / Watchdog”）的故障告警，说明受影响任务和原因；绝不自动充值或擅自切换付费账号继续执行。
- **合并恢复检查与接续**：同一额度池影响多个任务时合并告警与恢复检查；有可靠状态接口或用户显式允许低频探测时检查恢复，否则明确显示“等待恢复确认”。恢复后在原有效授权内自动接续，但不覆盖人工暂停、停止或撤销。

### 4.3 Watchdog 独立监督
- **独立于工作会话**：优先由确定性程序检查服务健康与可观察异常（明确报错、同错反复出现、等待条件已满足却未接续、执行者失联、已暂停却误启动新步骤），必要时辅以独立模型判断。
- **区分故障与疑点**：确定的运行故障可在授权范围内协助替换/恢复并遵守执行权唯一性；对进展缓慢等“疑点”只向当前负责人提供证据，不武断判失败或自行换方向；状态正常时不刷屏打扰。

### 4.4 完整记忆体系与遗忘失效传播
建立五层清晰分治的信息体系：
1. **用户通用规则与偏好**：单一权威来源，避免各 Bot 副本互相打架。
2. **Bot 跨项目经验**：方法、坑点、合作经验与来源项目简短引用，附带适用条件，不携带原项目事实与授权。
3. **项目档案**：目标、范围、决定及原因、事实、成果、进展与后续事项，可随项目移交完整继承。
4. **任务接续记录**：尝试过的路径、障碍、等待条件与下一步约定。
5. **原始资料**：对话、文档、日志与产物证据入口，记忆只存结论与引用，不保存密码、Token 等秘密值。

- **主动维护与遗忘传播**：在重要决定、纠正、交接和接续节点主动整理；用户纠正、限域或要求“忘记”时，默认保留原始对话供核查，但使受管记忆条目及其可追溯派生摘要失效，防止旧会话或旧记录将其重新复活为现行指令（同时明确：忘记偏好与撤销任务授权相互独立）。

### 4.5 渠道扩展
- 保持“统一工作室 + 可插拔私聊渠道”架构，后续可扩展微信等个人私聊入口，共享同一份任务连续性。

## 5. V1 必须为终态预留的架构接口

为避免 V2/V3 推倒重写，V1 在实现时应保持以下五个轻量预留点：

1. **实体主键分离**：SQLite 表结构中明确区分 `bot_id`、`project_id`、`task_id`、`session_id`，不把 Bot 身份与 Session 或模型名混为一谈。
2. **统一宿主拦截点**：所有 Worker 工具调用经过统一的宿主 `tools.guard` 管道，V1 挂载分级权限与路径校验，V2 可平滑插入语义 Guard。
3. **任务扩展字段**：任务账本预留关联附件/受管产物（`artifacts`）和外部作业引用（`external_job`）的扩展结构。
4. **模型与错误分类钩子**：模型路由层集中封装按角色/任务选模与 provider 错误识别，为 V2 精细调度与 V3 共享额度停池留出接入点。
5. **渠道适配解耦**：飞书通道仅作为 `StudioService` 的输入输出适配器，核心会话、任务与确认状态机不耦合任何单一渠道协议。

## 6. 明确不在规划内

- 群聊协作与复杂多用户权限体系；
- 自建 SSH、Slurm、容器集群等底层计算调度后端；
- 独立的强制交付 Reviewer 角色；
- 任务/日费用预测及复杂预算驱动自动降级引擎；
- 为每种工作预先建立固定部门或完整永久员工花名册。
