## 原型差异与设计前提

进入完整设计前，先核实关键运行时能力：宿主能否强制执行 Guard 所需的限制；各入口的有效更正能否及时登记，并在受影响的宿主动作启动或外部调用发出前使旧批准失效；多会话、交接和故障恢复时能否维持当前有效的管理权与执行权；额度耗尽时能否停止已有业务请求的底层自动重试并合并恢复检查。这些行为已是本基线要求，不能仅靠角色命名、提示词或状态展示就认为已经满足。

在已核对的原型版本 `456a120` 中，至少有以下运行时差异，不能只做配置替换：

- **动作约束：**原型的[会话初始化](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/src/app/sessions.ts#L137-L153>)将会话设为 `danger-full-access`；[执行说明](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/docs/003-execution.md#L23-L29>)写明以操作系统用户身份无审批运行命令，[CLI 包装器](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/src/infra/environment.ts#L1-L5>)也不构成操作系统级安全边界。原型的[请求与任务授权](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/docs/002-authorization.md#L1-L20>)不能直接替代本基线要求的动作拦截和执行约束。
- **长作业生命周期：**原型的[常规后台工作规则](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/docs/003-execution.md#L31-L47>)在有后台工作时保留 Worker 槽位，一轮结束后的常规等待上限为 30 分钟，超时会终止其管理的 shell 作业；Assignment 结束、插件停止或重启也涉及清理。[`workerIdle()`](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/src/executor/dsh.ts#L629-L658>)不能直接当作满足本基线的长作业等待机制。这里描述的是原型管理的后台工作，不代表任意外部计算系统中的作业都会被它终止。
- **入口指令登记：**原型的[Worker 消息处理](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/src/executor/dsh.ts#L488-L502>)不将用户直接在 Worker Session 输入的消息记入 Ticket，相关分支只更新 `personal` 时间；消息进入会话历史，不能视为已经更新统一任务控制依据。应优先验证宿主能否在 Worker 尚未读到 GUI 更正时，登记其控制效果并阻止受影响的旧动作；生效确认、重复投递及迟到消息的处理按[交互、渠道与自主性](interaction-and-delivery.md#交互渠道与自主性)约定。
- **底层重试控制：**原型的[额度重试健康监测](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/src/app/retry-health.ts#L1-L28>)只观察和展示状态，不修改重试策略；[会话健康说明](<https://github.com/Laxpud/super-agent/blob/456a120115ae0ca7846c44da41ee8a1bb1dbed1c/src/app/sessions.ts#L217-L226>)也明确模型和重试策略保持不变。应优先验证能否停止宿主或 provider 层已启动业务请求的自动重试，并统一安排允许的恢复检查。共享额度池的识别方式留给技术设计，不能假定模型名称、provider 配置名与实际额度池一一对应。

上述仓库代码不是底层 DSH 接口能力的完整证明，不能据此断言宿主不支持。无法满足宿主约束、重试控制或作业接口前提时，应明确报告不支持的能力和影响，不自动降级为 Full access，也不承诺无法观测的自动接续。核实这些前提不等于授权实施本次定制。

## 行为验收场景

以下场景用于判断定制后的行为是否符合本基线，可以用模拟消息和故障验证，不要求现在编写自动化测试、执行真实科研任务，或先选择数据库、队列和执行后端。它们不是对原型现状的完成声明。

技术设计应明确首版最低支持的动作类别、共享可变资源类型和长作业接续路径，以及 GUI／飞书等入口的指令登记、成果取得、共享额度池识别与重试控制方式。具体支持项与实现选择仍待技术设计确定。

对已声明支持的能力，模拟验证之外还应进行相应的实际运行验证：动作约束应验证真实执行入口确实受约束，共享资源修改应验证并发写入不会静默丢失内容，长作业路径应验证等待、执行槽位释放与接续能够完成；GUI 更正与额度停止也应核对实际控制状态和请求重试，而非只看聊天历史或健康说明。“不支持”说明不等于通过该项能力的验收。

首版实际运行验证应覆盖普通任务委派后取得成果、持续项目更正后接续、长作业等待后交付三条完整流程，可以使用小型示例资料，不要求预先提供真实科研任务。

| 场景 | 应当观察到的行为 |
| --- | --- |
| 简单写作或分析任务无须使用业务工具 | 仍委派 Worker；交付关联其结果，可以在原入口直接展示，不要求 Assistant 再改写一遍。 |
| 未立项任务需要多个 Worker 调查并综合结论 | 明确指定 Worker 负责技术整合和必要检查；不自动立项，Assistant 不自行补写技术结论，整合 Worker 不向其他 Worker 派工。 |
| 从飞书请求生成比较表，随后结束 Worker 会话并从 GUI 追问成果 | 原入口提供可访问的成果或可用的取得方式；需要保留的成果不因临时目录清理丢失，换入口仍能定位并取得已有成果，不要求重做。 |
| 从 GUI 交办 A，A 的受限动作等待确认；此时从飞书查询项目并交办 B，再用文字停止 A | 项目查询返回，B 可以被派发而无须先处理 A 的确认。停止只影响 A，不阻塞 B，也不把未确认动作变为已授权。 |
| 前台仍在处理一轮时，用户明确改变这一轮的方向，或另外交办独立工作 | 明确改向可介入旧轮；不发送旧方向的答复冒充当前结果。独立工作可以接收和处理，不默认取消旧任务；各结果可定位回原请求。 |
| 只在飞书私聊打字，查询待确认、批准一项、拒绝另一项，再查看这两项的状态 | 重要确认在私聊主聊天可见，用户不用点卡片或到网页操作。明确指向有效事项的文字与按钮按同样的规则校验；状态在网页也可核对，未指明对象的肯定和过期确认不生效。 |
| 已批准动作仍在工作室内部排队，尚未启动或发出调用，用户从另一入口要求缩小范围 | 更正登记生效后，受影响的旧批准失效，动作按新范围重新核对；不等待 Leader 阅读或批准更正。 |
| 用户在 GUI 直接更正 Worker 任务，Worker 尚未读到该消息 | 系统及时登记更正并阻止受影响的旧动作；只有任务依据和执行约束已更新，才能确认更正已生效，不以模型读到消息为生效前提。 |
| GUI 或飞书重复投递同一条消息，或已知较早的扩大范围指令迟到 | 不重复创建工作或视为新增授权，旧消息不覆盖已确认的新限制；跨渠道先后关系无法判断且影响动作时，澄清受影响的决定。 |
| 用户已暂停后续工作，又收到额度恢复和作业完成事件 | 不自动启动被暂停的后续业务；外部作业状态单独记录，暂停不被当成终止外部作业。 |
| 同一 Leader 的两个会话同时管理项目，或更换 Leader 后旧会话恢复 | 只有当前有效的管理实例能够新增派工和推进工作；旧实例可以提交已有成果，不能继续按旧身份指挥。 |
| Watchdog 在授权范围内恢复故障并替换执行轮次，原轮次随后恢复 | 原轮次不能重新取得执行权；当前轮次可接管已有结果，不形成两份并行推进的同一步骤。 |
| 任务范围、参数或目标版本变化后，旧执行实例按旧条件返回结果并报告成功 | 旧结果可以保留为历史或部分成果，当前负责人核对变化是否影响其适用性，仍适用的成果可以复用；不能仅凭旧实例报告成功就把当前要求标为完成，也不因无关更正使全部成果作废。 |
| 完成事件重复到达，状态查询同时发现完成，或接续期间服务重启 | 不重复推进同一步骤；接续采用当前负责人、任务状态和有效授权。 |
| 外部动作（包括作业提交）可能成功，但接收结果不确定或宿主在记录结果前中断 | 先核实实际结果；无法核实时显示“结果待确认”，不因缺少本地成功记录而直接重做。 |
| 外部系统已接受作业但尚在排队，用户要求暂停后续工作 | 不把外部排队当成工作室尚未发出的调用，也不自动取消作业；记录作业状态并暂停后续处理。用户另要求取消时，按工具能力处理并说明无法保证阻止的效果。 |
| 两个合法任务基于同一旧版本修改同一份首版支持的测试文档，或任务执行期间用户也修改了该文档 | 保留兼容的各方修改，或明确报告冲突；不能因为各自授权有效，就让后提交的结果静默覆盖其他任务或用户的修改。 |
| 有稳定引用和观测能力的独立长作业运行超过 30 分钟，Worker 已等待 | 作业不因等待超时而被终止，等待不持续推理或占用 Agent 执行槽位；正常会话结束和工作室服务重启不将其作为会话后台工作清理，满足接续条件后恢复。 |
| 外部作业缺少稳定引用或必要观测能力 | 明确说明不可自动观测，保留已知信息和接续条件；不把暂时未知当成失败或自动重新提交。 |
| 多个会话共用额度池并同时耗尽，包括 Assistant、Leader、Worker 使用同一额度池 | 无须再次调用该池即可记录状态并发送基本通知；原业务请求不持续产生新尝试，只保留合并后的可靠状态检查或配置允许的低频探测。无法检查时显示“等待恢复确认”，恢复后按当前有效授权接续原任务。 |
| 用户已授权一项宿主支持且范围明确的动作，例如删除选定算例的结果并保留输入文件 | Guard 依据已有授权直接放行，由执行方完成动作，无须用户再次逐字批准命令；实际效果限制在约定范围内，输入文件保留，且能查到授权依据与执行结果。 |
| Guard 审查超时或暂时不可用，尚未形成审查结果 | 不执行待审动作，也不视为已作出授权拒绝；服务恢复后可在当前有效指令和授权下继续审查，不要求仅因技术故障就提供新证据或重新授权。 |
| Guard 批准后，脚本、目标范围或授权依据变化 | 受影响的旧批准失效，按当前动作版本和有效授权重新核验；这不属于拒绝后的重复申请，同一命令文本也不能沿用旧批准获得新的副作用权限。 |
| Guard 已完成审查并明确拒绝，授权依据和实际效果未变，仅更换命令写法或包装脚本 | 不凭形式变化反复审查同一被拒绝效果；只有在获得能够影响判断的新证据、满足[纠错复核条件](action-authorization.md#拒绝与纠错复核)，或实质性缩小范围时才重新审查，无可行方案时说明真正的障碍。 |
| Guard 误读“保留输入文件”，据此拒绝已授权的结果文件清理，执行方指出原始指令与拒绝理由矛盾 | 允许有记录、有次数边界的纠错复核，不要求用户重复已有明确授权；复核期间不执行待审动作，业务 Worker 不能自行推翻 Guard，也不能靠不断换模型寻求放行。 |
| Worker 反复安装依赖失败，换模型、重新派工或咨询 Advisor 后仍重复实质相同的方案，且没有新的继续依据 | 当前负责人停止重复无效尝试，保存进展，将受影响工作标为受阻，报告具体障碍与可继续的条件；不因更换参与者或重复咨询就视为已有新策略。 |
| Watchdog 很久未看到进度，但没有确定故障证据 | 区分合理等待和进展疑点，向当前负责人提供证据；不直接判失败、改变方向或启动替代工作。 |
| 纠正或遗忘系统管理的经验条目后，恢复旧会话并读取其来源及可追溯派生记录 | 已失效的旧结论不会重新成为有效记忆或当前指令，也不能被旧 Worker 重新写回；不要求穷尽扫描全部历史自由文本，但当前决定和授权仍以最新有效记录为准，遗忘长期偏好本身不等于撤销任务授权。 |
| Worker 读取负责人指定的共享事实和其他 Worker 的成果 | 允许用于自己的任务；新增任务、改变共同约定或要求他人执行，仍经负责人安排。 |
| 用户跨渠道说“继续那个任务” | 能唯一定位就继续原任务；多个合理候选且会影响实质动作时才询问，不因换入口重复建任务。 |

## 暂缓选择与范围排除

下列事项已经讨论，但没有在当前基线中固定为具体实现承诺：

| 事项 | 当前结论 |
| --- | --- |
| 具体模型清单、排序和角色边界 | 允许组合、默认选择、升级条件和实际边界由用户配置；选择规则按[选择与调整](model-selection.md#选择与调整)，保留[此前已表达的 Advisor 偏好和模型限制](model-selection.md#此前已表达的模型选择)。 |
| 使用 DeepSeek 作为 Assistant | 可选方案，尚未选定，也不能代替不依赖模型的基本通知路径。 |
| 各类失败的具体恢复动作 | 额度恢复后的自动接续按[额度耗尽](model-selection.md#额度耗尽)约定；其他恢复动作随任务和后续指令决定，不固定统一重跑或修改参数矩阵。 |
| 并发数、检查周期和记忆实现 | 属于可调配置或实现细节，本文不承诺具体数值；额度恢复探测是否允许及其间隔按[额度耗尽](model-selection.md#额度耗尽)配置。 |
| 首批真实试用任务 | 按需要由用户选择，不作为整理需求或开始设计的前置条件；具备最小可用能力后，可以进行自愿试用。 |
| 纯 Router 与简单任务委派 | 当前保留所有业务任务委派的分工；可根据实际使用重新评估简短、无外部操作任务的委派成本，但未获用户明确调整前，不自行放宽 Assistant 的职责。 |
| Worker 直接澄清事实 | 首版保留经负责人转达的通信边界；实际出现大量事实澄清转述时，再由用户决定是否允许指定 Worker 在既定任务内有限交流，不预先建设横向通信协议，也不下放派工或修改共同约定的权限。 |
| 微信 | 后续渠道目标；首版入口为 DSH GUI 和飞书。 |
| 独立交付 Reviewer | 暂缓，不恢复为强制关卡。 |
| 自定义费用预测、日／任务支出上限、预算驱动降级 | 当前不做；额度停止与恢复按[额度耗尽](model-selection.md#额度耗尽)约定。 |
| 计算与执行环境基础设施 | 不建设或管理本地、SSH、cx05、Slurm 执行后端；宿主动作约束、沙箱能力接入和长作业生命周期协调仍在范围内，受[原型差异与设计前提](#原型差异与设计前提)约束。 |
| 群聊或多用户协作 | 当前不要求，不为首版建设复杂群组权限系统。 |
| 每项执行或机制都有永久 Bot | 不要求。避免固定部门、强制完整花名册，以及独立的长作业或维护角色。 |

此前推演了普通调查、明确立项的项目，以及长作业结束后继续处理等场景。它们用于说明上述要求，不是实际立项指令，也不要求现在执行这些任务。

本文没有选定存储引擎、配置格式、队列协议、界面布局、执行后端或实施里程碑。后续实现选择不能被表述成用户此前已经确认的需求。

## 已讨论的参考资料

下列来源曾用于讨论。列入参考不等于采用其框架、存储系统、默认设置或全部行为，也不构成依赖选择。

- [《Super-agent 设计探索：迈向更自主的 Agent 系统》](<https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg>)：统一 Router、隔离任务与异步交互。公开原型与文章设计并不完全一致，不能假设原型实现了所有提议。
