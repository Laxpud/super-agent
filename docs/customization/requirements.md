# 个人 AI 工作室定制：需求基线

> **状态：**记录截至 2026-11-16（Asia/Shanghai）讨论中已确认的需求与已采纳的默认约定。本文描述拟进行的定制，不表示原型已经实现这些能力。讨论中较晚的明确纠正优先于较早的提议。
>
> **文档范围：**整理已讨论并采纳的需求、行为边界和验收场景，以及不在范围内的事项和暂缓选择。本文不是实施计划、部署指令，也不授权开始开发、迁移数据或执行示例任务。

## 目标与范围

以当前 dsh-superagent 仓库为基础，定制一个供用户个人使用、面向通用工作的 AI 工作室。工作可以包括开发、科研、技术或论文写作、系统维护等。这些类别不是固定部门，也不与某个 Bot 或模型永久一一对应。

用户应当能够自然地交代工作，复用合适的 Bot 及其经验，让已授权工作自主推进，而不必反复说明上下文，或重复批准原指令已经覆盖的动作。系统应减少不必要的人类注意力消耗，同时保持责任明确、报告诚实和用户对工作范围的控制。

定制后的系统不局限于单个代码仓库。GitHub 仓库、Pull Request 或对外发布，不是所有任务的前提或统一交付形式。上游已有概念和集成是可以改造复用的实现基础，不应成为限制个人工作范围的产品约束。

首版只有用户本人能够下达指令，不建设群聊协作产品。本地、SSH、cx05、Slurm 等执行后端的建设、接入与执行环境管理，不属于本次定制的职责范围。宿主侧动作拦截、角色权限与沙箱能力的接入，以及后文约定的长作业生命周期协调与任务接续，属于本次定制范围；复用已有执行基础设施，不等于可以忽略这些运行时改造。

## 概念与身份

| 概念 | 在本次定制中的含义 |
| --- | --- |
| 角色 | 职责和权限边界，例如 Assistant、Leader、Worker。角色不是模型名称。 |
| Bot | 具有稳定身份的工作主体，拥有设定、合作偏好、积累的经验和过往工作引用。一个 Bot 可以有多个工作会话。 |
| 模型配置 | 某次使用所选择的 provider、模型及其支持的思考深度。它提供推理能力，不拥有 Bot 的身份或记忆。 |
| Session／会话 | 某一段工作的交互与执行上下文。新建会话不等于新建 Bot。 |
| 任务 | 一项有范围、负责人和预期结果的已请求或已授权工作。 |
| 项目 | 由用户明确立项的持续性工作，具有负责的 Leader 和持续维护的项目记录。不等同于仓库、目录或会话。 |
| 项目档案 | 项目目标、范围、决定、事实、成果、当前进展、已知问题及后续事项的记录。维护期间仍然有效，不是只有结项后才存在的归档材料。 |
| 长作业 | 运行时间超过一个 Agent 活动轮次的操作或外部过程。其执行生命周期与任务、会话分开。 |

Assistant 和 Leader 采用同一种 Bot 抽象，但不是合并成同一个 Bot 实例。Assistant 是面向用户的角色名，Router 是其内部架构名称。**Assistant 就是 Router，不是两个主体，也不是两层审批。**不再使用 Chief 作为该角色的名称。

更换 Bot 的模型，不等于创建新 Bot、更换项目负责人或丢弃记忆。新建或恢复会话，也应保留 Bot 身份。真正的负责人更换，是将项目从一个 Bot 交给另一个 Bot，而不是仅仅选择另一种模型。

系统应按需向选定模型提供持久化状态。这不保证不同模型表现完全一致，也不意味着积累经验会训练或改变底层模型权重。

## 角色与职责

### Assistant／Router

Assistant 是默认入口，但不是唯一入口。它理解和澄清要求、路由工作、安排合适的参与者、掌握整体状态，并向用户传达有价值的结果。

Assistant 不亲自执行业务或技术任务，包括简单任务。理解要求和路由工作需要必要的业务理解，但不因此获得自行完成分析、写作、实现或提出新技术结论的职责。不能因为它是统一入口，就让它接管项目内部的技术管理。

这项分工分为可由宿主强制执行的权限边界，以及需要通过行为验收约束的输出边界：

| 边界 | 约束方式 |
| --- | --- |
| 不运行业务命令、修改业务文件或调用业务 API | 由 Harness 的角色工具权限和宿主执行边界强制约束，不能只依赖提示词。 |
| 不自行完成应交给 Worker 的分析、写作和实现，包括无须工具的任务 | 通过角色提示词、交付来源、消息流程和行为验收约束；不能宣称仅靠工具权限即可保证。 |
| 理解和澄清要求、路由、查看状态、转达或概述已有成果 | 属于 Assistant 职责；需要新增技术判断或业务内容时，按既定角色职责安排 Worker 或 Advisor；项目内工作仍由 Leader 组织。 |

Assistant 展示的业务交付、咨询意见和项目汇总，应能追溯到实际承担相应职责的主体及其结果，包括 Worker 的执行成果、Advisor 的咨询意见，以及 Leader 的检查与整合。Assistant 可以转达或概述已有成果，但不能自行补充新的技术结论，也不能伪造或改变成果来源。

对于未立项工作，Assistant 安排 Worker，并作为 Worker 的直接负责人，负责任务安排、依赖协调和交付组织。需要技术整合或必要检查时，应明确指定承担这项任务的 Worker；可以由已经参与任务的合适 Worker 兼任，不必另建“整合 Worker”。需要专家判断时，可以安排 Advisor 提供分析。整合 Worker 不获得给其他 Worker 派工的权限，这种安排也不自动形成项目或持久 Leader。

对于已立项项目，除非用户指定负责人，否则由 Assistant 安排或选择 Leader。可以复用已有合适 Bot；新项目不必自动新建 Bot，也不必预先创建完整团队。

Assistant 可以建议立项，但不能把自己的建议当成用户已经作出的立项决定。

### Leader

每个明确立项的项目都有且只有一个当前负责的 Leader，不允许多个 Leader 同时管理同一个项目。同一个 Leader Bot 可以同时负责多个项目，也可以积累经验并在之后继续负责其他项目，不与单个项目永久绑定。各项目仍保持分开的工作上下文。

Leader 维护项目目标和范围，组织任务及依赖关系，分配 Worker，整合成果、识别遗漏并报告整体进展。其责任跨越阶段、会话和维护工作，不随一次派工结束而消失。

Leader 应尽量不亲自承担技术执行。这是通过系统提示词引导的分工要求，不通过工具权限禁止 Leader 进行技术执行。它需要理解必要背景，以组织工作和判断成果是否解决问题，但不能因为任务困难，就把自己变成最强的执行 Worker。

Worker 遇到困难时，Leader 可以识别障碍类型、调整任务或补充信息、咨询 Advisor，或选择更合适的执行模型和思考深度。这些手段互补，不规定统一的先后顺序：

- 方向不清、存在争议或难以判断时，可以咨询 Advisor。
- 方向明确而执行能力不足时，可以调整 Worker 的模型配置。
- 信息缺失或任务拆分不当，不一定要靠更昂贵的模型解决。
- 咨询 Advisor 不替代执行；升级执行模型，也不能排除本来需要的咨询。

**Leader 在共同配置范围内，直接分配项目内 Worker 并选择其模型配置，不需要请求 Assistant／Router 代办、批准或转述每次交流。**

### Worker

Worker 承担已分配的调查、实现、分析、写作等实际执行工作。“更强的 Worker”通常表示选择能力更合适的执行配置，不意味着新增组织级别，也不必创建新的永久 Bot。

Worker 向该任务的直属 Leader 汇报；任务没有 Leader 时，向 Assistant 汇报。Worker 之间不自行发起横向沟通、协调或派工，也不能通过共享记录间接要求其他 Worker 执行或改变共同约定。读取负责人指定的共享事实和其他 Worker 的成果，不属于横向派工，具体边界见[归属与读取](#归属与读取)。Worker 不能创建子 Worker 或继续向下派工；需要拆分或补充工作时，向负责人提出建议。

Worker 的执行受用户任务和授权范围约束。完成调查，不等于获准继续实现、安装、发布或自行立项。

不要求所有 Worker 都拥有永久 Bot 身份。有实际复用价值时，可以保留专业执行 Bot；首版不要求建立完整的永久员工花名册。

### Advisor

Advisor 针对方向不明、争议和困难问题提供专家分析。Leader 可以直接咨询 Advisor，不需要 Assistant 协调或转述。未立项工作由 Assistant 安排所需咨询，不因此新增 Leader。咨询按需围绕明确问题发起，不是所有困难任务的强制前置步骤，也不要求为复述同一意见额外调用 Worker。

Advisor 提供判断和建议，Worker 承担执行。同一个模型可以用于这两种角色，但不能因此混淆职责。更强的执行模型也不是只能用于 Advisor。

### Guard

Guard 依据用户已有指令，代用户对待执行动作作出授权判断。它不是交付质量 Reviewer，也不是把常规审批请求转交给用户的中转。具体要求见动作授权部分。

### Watchdog

Watchdog 独立检查服务健康、任务进展、停滞和可能的目标偏离，并在授权范围内协助报告或恢复问题。它不是第二个项目经理，也不是替代技术负责人。具体要求见监督与故障通知部分。

### 暂缓的角色

暂不设置独立的交付 Reviewer。Leader 对成果进行检查和整合，是负责人的正常职责，不能以此变相恢复独立 Reviewer 角色。

每一种职责都不必对应一个独立常驻服务、持续运行的模型会话、独立公开聊天账号或人格。各角色可以共用调用和任务机制，按职责配置权限、输入和输出。不新增长作业角色或维护角色。

## 立项、负责人和长期维护

由用户用自然语言明确立项，不要求固定命令或关键词。但把某个目录或仓库称为“项目”，本身不等于发出了立项指令。

不能仅根据复杂度自动设置 Leader。未立项工作也可以很深入；Assistant 可以建议立项，但决定仍属于用户。

用户可以指定或更换 Leader。没有指定时，Assistant 选择或创建合适的 Leader Bot。项目子任务继承已有项目的负责人关系，不能只因新增一个任务就再设置一个 Leader。

已有工作后来正式立项时，应在原上下文和已完成成果上接续，不要求用户重新说明一遍，也不重做已经完成的工作。

任务完成、阶段完成和项目持续存在，是不同层次：

- 任务负责人交付约定结果及必要依据后，可以报告完成，不要求用户逐项批准所有小任务。
- Leader 可以报告约定阶段已经完成。
- 项目可以继续进入维护或后续迭代，保留负责人和记录。
- 每次交付后不必经过正式结项。需要结项、停止维护或归档时，由用户决定。

长期负责不等于持续推理。没有待办、相关事件或已授权维护活动时，Bot 保留责任和记录，不反复思考、通过模型轮询或自行找新工作。

维护范围与恢复行为可以随用户指令变化。现在不为所有工作统一规定重试、重启、修改参数或重跑策略。

### 当前管理权与执行接续

“一个当前 Leader”不仅表示 Bot 身份唯一，还表示同一项目只有一套当前有效的管理权。同一个 Leader 的多个会话，不能各自独立决定并重复推进项目的下一阶段。

同一任务的同一执行步骤，不能由多个恢复实例重复推进。负责人更换或执行轮次替换后，旧实例可以提交已经取得的成果和执行记录，但不能继续新增派工或推进业务执行。原有任务和成果由当前有效的负责人或执行实例接管；这不限制项目内多个 Worker 并行承担不同工作。

作业完成事件、状态查询、Watchdog 恢复和服务重启，都应遵守上述规则。重复事件不能重复启动同一步骤；被替换的轮次后来恢复，也不能重新取得执行权。

接续前，应核对当前负责人关系、任务状态、最新有效指令和授权。人工暂停、停止或撤销不能被额度恢复、作业完成等事件覆盖。会话恢复不等于原有派工权或动作批准仍然有效。

不承诺所有外部副作用都严格只发生一次。外部动作可能已经成功，而宿主尚未来得及记录结果；这种情况下应先核实实际结果，无法核实时标为“结果待确认”，不能仅因本地缺少成功记录就重复执行。

上述要求约束当前运行架构中的有效任务状态和执行归属，不预设跨机器部署、选主或复杂分布式协调机制。

## 交互、渠道与自主性

### 指令来源与入口

当前只有用户本人可以下达指令。采用常规身份白名单即可，群聊协作和复杂群组权限模式不属于当前需求。

用户可以通过 Assistant 交代工作，也可以进入任务，直接与 Leader 或 Worker 讨论细节。直接交流仍属于原任务，不会悄悄改变负责人或汇报关系。重要的范围变化和项目决定应让相关负责人可查，不能只留在孤立的聊天中。

首版以 DSH GUI 和飞书为主要入口。微信是后续扩展目标，不是首版前提。渠道应可扩展，不能每个渠道各自形成一套互不相干的工作室。

用户的私聊入口共享任务连续性：可以在一个入口发起任务，在另一个入口追问或调整。这不等于把所有聊天拼成一个上下文、广播所有消息，或将私人上下文带入未来的群聊。当前不要求群聊；以后引入时，也只共享明确放进去的任务和信息。

跨渠道说“继续那个任务”时，能够唯一定位就接续该任务；存在多个合理候选，且选择会影响实质动作时，才询问任务归属。不能因为入口改变就新建一份重复任务。

### 更正、撤销与暂停

用户直接向 Assistant、Leader 或 Worker 发出的有效指令，效力不取决于负责人是否已经阅读或再次批准。系统应将重要变化纳入当前任务依据，并让相关负责人可查；“可查”不能代替执行前实际采用新要求。

- 系统确认收到针对相应任务的停止、撤销或范围缩小后，受影响的待执行动作不得按旧范围启动，相关旧批准失效。不需要等待 Leader 再批准用户的更正。
- 动作实际开始前，核对当前有效授权和约束。已经排队、已经派工或曾经获批，都不是继续使用旧授权的理由。
- 对已经开始的动作，按当前指令和工具能力处理，并如实说明已发生的效果、能否中止和仍不确定的部分，不能声称尚未发生或保证可以撤回。
- “暂停后续工作”与“终止正在运行的外部作业”分别记录和处理，不能自行将两者等同。后续处理被暂停时，仍可记录外部作业状态，但不能因完成或额度恢复事件自动启动后续业务；终止外部作业仍须符合用户指令和动作授权。

### 自主性

在已交代的工作范围内，负责人应主动推进必要且已授权的步骤。已明确授权的持续目标或维护范围，可以持续推进，不必每个子步骤重新请求一次。

对于范围外的新工作，系统可以提出建议，但不能仅因某个 Bot 发现机会就自行开工。外部文档、工具结果和其他参与者可以提供证据，不能成为新增人类授权。

确实缺少业务决定时可以澄清，但不能把已经授权的动作重新包装成审批问题。

### 汇报与交付

默认简洁汇报，必要时展开细节。报告有意义的进展、最终结果和实质性障碍，不反复报告正常作业“仍在运行”。

交付应说明完成了什么、依据是什么、还有什么未完成或不确定。工具返回成功、代码已写出、作业已提交，都不等于任务完成。交付也不统一要求是 Pull Request 或对外发布。

简单任务可以只委派一个 Worker，并在原入口直接展示其结果，保留任务归属和交付来源。不要求为转述同一份答案再调用一次 Assistant。

## 模型选择与配置

### 共同配置，各自负责

提供可配置的调度偏好，默认优先顺序是：**效果 → 费用 → 速度**。这里的效果优先，是先满足任务必需能力和约定的交付要求，再在预计能够满足要求的组合中比较费用和速度；不是只要更强配置可能带来一点改善，就一律选择最高档。

允许用户从当前实际可用的模型及其支持的思考深度中，自定义组合、排序，并设置各角色的能力下限和上限。选择对象是具体的“模型与思考深度组合”，不只是模型名称。

Assistant 和 Leader 在安排各自负责的工作时，遵守这份共同配置。共享配置不意味着把所有选择集中到 Assistant；Leader 为项目分配执行模型，不需要向 Router 发请求。

调度应遵守角色边界和允许的组合。效果优先不能成为越过角色上限的理由；上限也不是每个任务都直接使用最高档的指令。不能用模型名字或思考深度标签代替有依据的能力判断，也不能虚构模型并不支持的组合。

如果用一维排序表达能力上下限，它首先是用户的调度偏好，不是模型在所有任务上的统一能力排名。写作、图像理解、工具使用等任务的必需能力，仍需分别满足。

### 选择与调整

首版采用用户定义的允许组合、默认选择和升级条件，不要求建设复杂的能力评测平台：

1. 先满足角色允许范围和任务必需能力，排除不支持所需输入、工具或执行方式的组合。
2. 根据任务类型、用户配置和已有可靠经验选择默认组合。普通任务选择预计能够满足交付要求的配置，不默认使用角色上限。
3. 对高难度任务，或用户已明确要求优先追求质量的任务，在允许范围内使用更强、更适合该任务的配置。
4. 能力不足或结果不达标时，可以升级执行配置；信息缺失时，应补充资料或澄清；任务拆分和方向有问题时，应调整任务或咨询 Advisor。不能把所有问题都当作模型档位不足。

### 此前已表达的模型选择

讨论中保留用户此前对 Advisor 的参考选择：**GPT-6-Astra，思考深度 `max`**。这是用户偏好的记录，不是新的能力评测，也不表示本文已经核实其当前可用性。

保留此前对 **DeepSeek-Pro** 的限制：暂不用于工作。曾提到未来可能尝试用它改善写作自然度，但效果尚不确定；本文不启动或承诺该实验。这不等于禁止使用所有 DeepSeek 模型。

使用 DeepSeek 作为 Assistant，曾被讨论为避免共用 GPT 额度池的一种可能选择，但尚未选定。其他角色的具体配置、完整候选排序，以及数值或枚举形式的能力边界，仍待配置。不把此前未经可靠核实的排名、价格或能力说法当作事实。

### 额度耗尽

现阶段不建设任务或日预算、费用预测，以及复杂的预算驱动降级策略。实际可用额度耗尽、工作无法继续时，停止受影响模型的业务调用和新调度，并保留已有的持久化进展。仅允许按下述条件进行恢复检查。已经运行的外部作业继续运行，不因模型额度耗尽而终止。

记录额度错误和工作状态，不依赖已经没有额度的模型再生成最终总结。应区分明确的额度耗尽与临时限流、连接异常。一个额度池受影响，不等于所有无关工作都必须停止。

不能假设 Assistant 还可以推理：Assistant、Leader 和 Worker 可能共用同一已耗尽额度池。不依赖该模型的通知路径见监督部分。不能自动充值，或额外切换账号、付费渠道来绕过停止。备用通知路径不等于获准继续使用其他付费执行路径。

系统能否自动发现恢复，取决于 provider 的能力和允许的检查方式：

| 条件 | 恢复检查行为 |
| --- | --- |
| 有可靠状态接口、重置时间或恢复事件 | 根据相应信号检查恢复；不能仅因一个不可靠的预计时间已到，就认为恢复。 |
| 没有独立状态接口，且用户配置允许探测原额度池 | 按配置进行受控、低频的恢复探测，不恢复普通业务调用，也不让每个等待任务分别尝试。 |
| 没有可靠检查能力，或用户配置未允许必要的探测 | 明确显示“等待恢复确认”，保留接续条件，不承诺自动发现恢复，也不自行发起模型请求探测。 |

同一额度池影响多个任务时，合并恢复检查和故障通知，说明受影响的工作，不为每个任务重复探测或反复报告同一故障。具体探测间隔后续配置；恢复探测不授权换账号、换付费渠道或绕过用户暂停。

额度恢复后，允许在原任务和当前有效授权范围内自动接续，无需仅因额度曾耗尽而重新请求批准。例如 Watchdog 发现工作已经具备恢复条件时，可以唤醒当前负责人，或由 Assistant 接续协调。恢复仍须遵守[当前管理权与执行接续](#当前管理权与执行接续)，不改变角色职责或负责人关系，也不能覆盖人工暂停、停止或撤销。

## 代用户进行动作授权

### 目的与边界

Guard 在受支持的动作类型和可约束范围内，判断具体待执行动作的实际效果是否符合用户已经作出的授权。用户已经授权某项操作及其范围时，不应再要求逐字批准实现该操作的命令。审查不能穷尽预测任意程序的所有运行效果，执行过程也必须被限制在获准范围内。

例如，用户要求清理选中的算例结果、保留输入文件，Guard 可以放行目标和范围相符的删除动作，不能放行删除其他算例或输入文件。缺少“选中了哪些算例”的上下文时，应先查找证据，而不是立即要求用户重复批准。

动作风险与授权充分程度是两种判断。高风险动作可能正是用户明确要求的；看似普通的动作也可能超出范围。用户希望达到一个目标，不等于授权任意实现手段或额外副作用。

Guard 不是常规人工审批转发通道，其处理方式是：

1. 检查待执行动作，以及相关原始指令和上下文。
2. 对能够影响判断的缺失证据进行补查。
3. 符合已有授权和有效约束时，直接放行。
4. 否则不执行，将原因返回负责执行的一方，使其缩小动作范围、采用已授权的替代方式，或指出真正缺少的决定。

确实尚未解决的业务决定，仍可由负责角色澄清。但换一个角色转发同一张工具审批单，不属于这种澄清。审查失败或证据不足，不是默认放行的理由。

对于已经完成审查并明确拒绝的动作，在授权依据和实际效果均未改变时，只有获得新证据或实质性缩小动作范围，才重新审查。更换命令写法、工具或包装脚本，不是反复尝试同一被拒绝效果的理由。无法形成可执行方案时，记录具体受阻原因；确实缺少用户决定时，由负责人报告该缺口，不无限重试或重复发送同一个审批问题。

审查暂时不可用、尚未完成，或原批准因动作版本变化失效，不等于已经作出了授权拒绝，按既有恢复和重新核验规则处理。尚未形成有效批准时，仍不得执行待审的业务动作。

### 依据与作用范围

Guard 需要能够查到用户的原始要求、相关跨渠道补充、限制与撤销、任务范围，以及本次待审的具体动作。

Assistant 或 Leader 可以在范围内转交和细化工作，但不能凭自己的说法扩大用户授权。Worker 自述、生成的摘要、检索文字和学习到的经验，不能冒充用户指令。用户曾在一个项目中允许某项动作，不代表另一个项目也获得同样授权。

批准应与实际动作、目标、参数、相关脚本效果及当前有效授权对应。动作、脚本、目标范围、参数或授权依据变化后，受影响的旧批准失效，不能继续使用针对另一种效果或旧授权的批准。不能只看 shell 命令或工具名，还要检查文件操作、工具、网络发送等实际副作用。

动作实际开始前必须核对当前有效授权，不能只在最初派工或审查时检查一次。即使命令文本没有变化，用户后来缩小范围或撤销授权，也应按[更正、撤销与暂停](#更正撤销与暂停)使受影响动作停止使用旧批准。

### 强制执行与成本

保留受限执行环境，并由宿主强制执行可约束的角色工具权限和动作边界，不能只依赖提示词纪律，或永久设置 `danger-full-access`。角色职责中的提示词引导不等于取消用户授权范围、沙箱或 Guard 动作审查的约束。模型审批不能代替沙箱，也不能保证无工具的文本输出遵守全部角色分工。

本次定制包括接入宿主提供的动作拦截、角色权限与沙箱能力，不包括另建本地、SSH 或 Slurm 执行后端。应先验证宿主能否强制执行所需限制；宿主不能约束的动作，明确标为不支持或受阻，不能为了执行而自动降级为 Full access。原型已有的请求准入和任务授权，不能直接视为已经具备 Guard 的动作级执行约束。

脚本的实际效果可能取决于随后读取的配置、符号链接或远端响应。看过脚本不等于已确认其全部效果；无法确认或限制效果时，应改成可约束的操作，不能仅凭审查意见获得任意副作用权限。

对于明确允许的常规操作，采用确定性处理，不要求每条工具调用都额外调用一次审批模型。需要理解授权与实际效果时，再使用模型判断。获准的额外权限只服务于有边界的具体动作，不形成永久通用授权。

Guard 可以调查，但不亲自执行被批准的业务动作，不在审查时修改目标，不给自己提权，也不放宽其他角色的职责。Assistant 不能因为工具能获批就开始执行业务；Watchdog 的恢复也不能成为绕过审批的旁路。

Codex CLI 的 `Approve for me`／Guardian 是具体参考：受限的基础执行环境、针对动作的审查、真实用户授权上下文，以及可强制执行的允许或拒绝结果。但它的人工回退分支和固定策略，不自动成为本系统要求。也不能认为只要启用 DSH 实验性逐调用 Auto review，就已经满足本需求，因为其获准动作以 Full access 执行。

## 长作业协调

提供通用的长作业等待与接续机制，不专用于仿真，不增加新的 Bot 角色，也不承诺建设本地、SSH、Slurm 执行后端或计算调度器。

自动等待与接续适用于现有工具能提供稳定作业引用，并有状态查询、结果入口或完成事件等能力可用于判断接续条件的作业。“通用”表示可适配不同来源，不表示能够自动理解或观测任意外部进程。缺少必要能力时，应说明不可自动观测，保留已知作业信息、缺失能力和接续条件。

首版可以先走通一条满足上述前提的现有作业路径，并保留扩展接口，不要求同时适配所有本地、SSH、Slurm 或其他任务系统。

任务、Bot／会话和外部长作业的生命周期分开。保留稳定的作业引用、任务归属、状态、结果或日志入口，以及约定的后续处理，不能让某个空闲模型会话成为唯一记录。

对支持独立运行的长作业，Worker 等待、会话或 Assignment 结束、额度耗尽，以及工作室服务正常停止或重启，都不能成为清理并终止作业的理由。作业能否继续运行仍受实际执行环境约束，不保证主机或外部服务故障后继续存活；缺少独立运行能力时，不能宣称满足这项要求。

作业运行期间，负责的 Worker 可以进入等待；等待后释放 Agent 的执行槽位，不维持活动推理循环，也不因仍有外部作业运行而长期占槽。等待不代表完成或放弃任务；已立项项目的 Leader 仍保持整体责任。

优先利用已有状态信号或低成本的程序检查。完成、失败、重要变化或需要判断的情况，可以唤醒负责人。程序定时检查与定时唤醒模型是两种不同机制，后者不是默认监控方式。

恢复工作时提供必要的变化摘要、下一步和资料入口。完整历史与日志应可查，但不反复注入全部检查记录或整份日志。继续原任务上下文，并遵守[当前管理权与执行接续](#当前管理权与执行接续)；完成事件和状态查询同时到达，也不能创建重复工作。

暂时无法查询作业时，应认为状态未知，而不是认定失败，不能因此推断需要重新提交或重复执行。作业成功结束后，也可能还有分析、后处理或汇报任务。

外部作业的恢复、重试、检查点续跑、修改参数和从头重跑，依具体工作和当前授权决定。额度恢复后的任务自动接续按[额度耗尽](#额度耗尽)约定处理，不等于自动重跑外部作业。现在不为所有作业固定这些策略。

## 监督与故障通知

### Watchdog 巡查

Watchdog 位于被检查的工作会话之外，检查范围包括基础服务健康与实质性工作进展，例如停滞、反复无效尝试、遗漏后续处理和可能的目标偏离，不只检查进程是否存在。

首版主要依据已有状态、错误和事件，识别以下可观察异常：

- 服务、会话或工具明确报错。
- 同一种失败反复出现。
- 等待条件已经满足，后续工作却没有启动。
- 任务记录显示已暂停后续工作，却仍有新的后续业务启动。
- 任务仍显示由某个执行者运行，但该执行者已经失效或消失。

优先由程序检查，必要时使用模型形成判断依据。不要求 Watchdog 持续独立审读全部工作内容，或全面评价科研方向、论文论证等深层语义问题；这类技术判断由当前负责人处理，必要时按职责咨询 Advisor。具体检查覆盖和判断方式在技术设计中明确。

确定的运行故障，与对进展或方向的疑点，应分别处理。对后者提供证据并通知当前负责人判断，不能仅凭“很久没更新”就认定失败、改变技术方向或启动另一份工作。对确定故障的恢复，也必须在已有授权范围内，并遵守[当前管理权与执行接续](#当前管理权与执行接续)。

它应区分合理等待、额度停止、人工暂停与本应继续推进的任务。尊重明确停止和挂起，不自动重启人工停止的工作，只在授权范围内执行恢复。不能为了方便恢复而修改用户要求或绕过 Guard。

独立 profile 或进程有助于隔离，但不能据此承诺在共享主机故障后仍然可用。具体检查周期和每种恢复动作尚未固定。状态正常或没有变化时，不应反复通知。

### 不依赖耗尽额度池的通知

即使 Assistant 与工作共用已耗尽的额度池，额度故障仍应能够报告：

1. 宿主依据已有持久化进展，记录错误和受影响工作状态，不要求再成功调用一次模型。
2. Watchdog 或基础程序巡查发现停止的工作。
3. Assistant 仍可用时，可以交由它汇总或转达。
4. Assistant 无法推理时，直接通过它已配置的用户渠道发送基本通知，不经过 Assistant 的模型。

Watchdog 自身的基本通知路径，也不能完全依赖同一个已耗尽额度池。可以使用独立可用的模型服务，或由程序完成明确状态的巡查和发送。这属于监督机制，不新增通知 Bot 角色。

直接发送的消息应标明来源，例如 Watchdog 或系统通知。使用 Assistant 的渠道，不代表 Assistant 那个不可用的模型已经分析过此事件。通知说明受影响工作和停止原因，并保持“备用通知”与“获准换渠道继续花费执行”的区别。

## 记忆与项目档案

### 归属与读取

**跨项目经验跟 Bot 走，项目事实跟项目档案走。** Bot 需要细节时可以返回查阅档案，不必将所有项目事实持续放在每个活动上下文中。

| 内容 | 处理方式 |
| --- | --- |
| 用户的通用规则与偏好 | 保留用户明确表达的长期要求和合作偏好，保持一致的共同依据，避免各 Bot 中出现互相矛盾的副本。 |
| Bot 经验 | 保留适用方法、实际坑点、纠正、合作经验，以及过往项目的简短引用。按相关性复用，保留条件与依据。 |
| 项目档案 | 维护目标、范围、当前决定及原因、事实、成果、进展、已知问题和后续事项。由负责 Bot 管理，但不能成为其他负责人无法接管的私人知识。 |
| 任务接续记录 | 保存做过什么、尝试过什么、当前障碍或等待条件、下一步约定。只将有长期价值的结论提炼到更广范围。 |
| 原始资料 | 保留对话、文档、成果和日志等证据入口。记忆保存必要结论与引用，不穷尽复制所有原文。 |

同一个 Leader Bot 可以把某项目的经验用于另一个项目，但不能悄悄带入前一个项目的假设、当前事实或授权。通用方法可以跨项目借鉴；项目事实应在对应上下文中查阅，不能当成普遍规则。

Bot 可以拥有工作笔记和专业经验，但项目关键知识不能只有一份藏在不可替代的私人对话里。更换负责 Bot 后，应仍可根据项目记录继续工作。项目记录在物理上可以存放于当前 Bot 的工作空间；这不等于已经选择中央数据库或某种存储后端。

经验有归属，不要求独占存储或为每个 Bot 复制一套方法库。经验可以由负责 Bot 维护来源、适用条件和当前结论，其他 Bot 在相关任务和允许的读取范围内引用。临时 Worker 的可复用成果可以进入项目记录，或由负责 Bot 有意提炼，不必仅为保存经验将其转为永久 Bot。

共享记录用于相关事实、决定和状态，不是无限制的全员聊天或 Worker 横向派工。Worker 可以读取负责人指定的共享事实和其他 Worker 已交付的成果，例如负责技术整合的 Worker 读取各篇论文的调查结果。需要新增任务、改变共同约定或要求其他 Worker 执行时，仍经负责人安排，不能通过共享记录发号施令。

Leader 负责项目共同状态的一致性；未立项工作由 Assistant 组织交付，技术整合与检查仍由指定 Worker 承担。与用户的直接讨论不能使重要范围变化脱离当前任务依据和负责人的组织责任。

### 主动记录与纠正

系统主动整理和维护记忆，不要求用户逐条发出写入指令。应在重要决定、纠正、交接和接续节点记录，不要求每条消息后都额外调用一次模型总结。

区分当前事实、决定与假设、观察。单次成功可以带条件记录，不能写成普遍验证过的方法。一次性任务指令不能悄悄变成永久偏好。长期要求应具有明确的长期适用意思，不要求某个固定口令。

决定发生变化时，更新当前有效结论，保留有用原因或历史，不能让相互矛盾的旧指令同时生效。某个项目的改变，不自动适用于所有其他项目。

不把密码、令牌等秘密值存为普通记忆；需要定位相关配置时使用受控引用。学习到的经验不能改变硬性职责边界、创造授权或覆盖较新的明确指令。

### 查看、修正与遗忘

用户可以用自然语言询问记住了什么、某个结论从何而来，也可以纠正、限制到某个项目，或要求忘记。

“忘记这条”表示不再将该内容作为长期记忆使用，并避免以后从旧记录中又自动提炼回来；默认不删除原始对话、文档或项目成果。删除原始资料需要用户另行明确范围。

纠正、限制或遗忘后的失效状态，也应约束派生摘要、检索结果、历史迁移和之后恢复的旧会话。旧资料可以作为历史证据读取，但不能使过时结论重新成为有效记忆或当前指令；旧 Worker 也不能将其作为现行结论重新写回。

失效传播以系统管理的记忆条目、来源和可追溯派生内容为对象，不要求穷尽识别全部历史自由文本中的语义等价表述，也不要求反复用模型扫描全部历史。检索和接续时提供当前有效结论，写入时阻止已知失效内容重新成为现行记录。这个范围说明不削弱执行约束：已经纠正的当前决定、已经撤销或缩小的授权，仍必须以最新有效记录为准。

忘记某条长期偏好，与撤销一项任务授权是两种操作，不能自动互相推导。用户同时提出两者时分别生效；保留原始记录供核查，不表示其中已失效的内容仍有效。

与授权有关的记录应保留可追溯的依据、来源和作用范围。摘要可以帮助定位授权，不能凭空创造授权或抹去原始限制。读取旧记录时，当前有效的限制和撤销仍然适用，动作执行仍按[更正、撤销与暂停](#更正撤销与暂停)处理。

## 初始资料与既有历史

以本轮讨论确认的要求作为新基线。已有 DS Bot 设定、对话、项目文档、工作规范和技能，可以作为历史来源或记忆候选，不自动成为现行指令。

不恢复用户已经纠正或撤回的要求。特别是旧 Chief 命名、按复杂度自动设置 Leader、独立 Reviewer、记忆全部绑定单一项目或 Bot、由 Router 集中分配项目 Worker，以及依赖模型推理的额度故障报告，都不是当前设计。

按需要迁移有价值的材料，不要求预先全量导入。具体迁移范围尚未选择。将迁移或写作实验写入本文，不代表已经授权执行。

## 原型差异与设计前提

进入完整设计前，先核实三项运行时能力：宿主能否强制执行 Guard 所需的限制；用户新指令能否在受影响动作开始前使旧批准失效；多会话、交接和故障恢复时能否维持当前有效的管理权与执行权。这些行为已是本基线要求，不能仅靠角色命名或提示词就认为已经满足。

与本轮核对的原型版本 `8a62c8a` 相比，至少有两处需要运行时改造，不能只做配置替换：

- **动作约束：**原型的[会话初始化](<https://github.com/Laxpud/super-agent/blob/8a62c8a9056538161b000e3abe62ac0213da9b6a/src/app/sessions.ts#L137-L152>)将会话设为 `danger-full-access`；[执行说明](<https://github.com/Laxpud/super-agent/blob/8a62c8a9056538161b000e3abe62ac0213da9b6a/docs/003-execution.md#L23-L29>)写明以操作系统用户身份无审批运行命令，[CLI 包装器](<https://github.com/Laxpud/super-agent/blob/8a62c8a9056538161b000e3abe62ac0213da9b6a/src/infra/environment.ts#L1-L5>)也不构成操作系统级安全边界。原型的[请求与任务授权](<https://github.com/Laxpud/super-agent/blob/8a62c8a9056538161b000e3abe62ac0213da9b6a/docs/002-authorization.md#L1-L20>)不能直接替代本基线要求的动作拦截和执行约束。
- **长作业生命周期：**原型的[常规后台工作规则](<https://github.com/Laxpud/super-agent/blob/8a62c8a9056538161b000e3abe62ac0213da9b6a/docs/003-execution.md#L31-L47>)在有后台工作时保留 Worker 槽位，一轮结束后的常规等待上限为 30 分钟，超时会终止其管理的 shell 作业；Assignment 结束、插件停止或重启也涉及清理。[`workerIdle()`](<https://github.com/Laxpud/super-agent/blob/8a62c8a9056538161b000e3abe62ac0213da9b6a/src/executor/dsh.ts#L629-L658>)不能直接当作满足本基线的长作业等待机制。这里描述的是原型管理的后台工作，不代表任意外部计算系统中的作业都会被它终止。

无法满足宿主约束或作业接口前提时，应明确报告不支持的能力和影响，不自动降级为 Full access，也不承诺无法观测的自动接续。核实这些前提不等于授权实施本次定制。

## 行为验收场景

以下场景用于判断定制后的行为是否符合本基线，可以用模拟消息和故障验证，不要求现在编写自动化测试、执行真实科研任务，或先选择数据库、队列和执行后端。它们不是对原型现状的完成声明。

技术设计应明确首版最低支持的动作类别和长作业接续路径。对已声明支持的能力，模拟验证之外还应进行相应的实际运行验证：动作约束应验证真实执行入口确实受约束，长作业路径应验证等待、执行槽位释放与接续能够完成。“不支持”说明不等于通过该项能力的验收。

| 场景 | 应当观察到的行为 |
| --- | --- |
| 简单写作或分析任务无须使用业务工具 | 仍委派 Worker；交付关联其结果，可以在原入口直接展示，不要求 Assistant 再改写一遍。 |
| 未立项任务需要多个 Worker 调查并综合结论 | 明确指定 Worker 负责技术整合和必要检查；不自动立项，Assistant 不自行补写技术结论，整合 Worker 不向其他 Worker 派工。 |
| 已批准动作尚未开始，用户从另一入口要求缩小范围 | 系统确认收到后，受影响的旧批准失效，动作按新范围重新核对；不等待 Leader 阅读或批准更正。 |
| 用户已暂停后续工作，又收到额度恢复和作业完成事件 | 不自动启动被暂停的后续业务；外部作业状态单独记录，暂停不被当成终止外部作业。 |
| 同一 Leader 的两个会话同时管理项目，或更换 Leader 后旧会话恢复 | 只有当前有效的管理实例能够新增派工和推进工作；旧实例可以提交已有成果，不能继续按旧身份指挥。 |
| Watchdog 在授权范围内恢复故障并替换执行轮次，原轮次随后恢复 | 原轮次不能重新取得执行权；当前轮次可接管已有结果，不形成两份并行推进的同一步骤。 |
| 完成事件重复到达，状态查询同时发现完成，或接续期间服务重启 | 不重复推进同一步骤；接续采用当前负责人、任务状态和有效授权。 |
| 外部动作可能成功，但宿主在记录结果前中断 | 先核实实际结果；无法核实时显示“结果待确认”，不因缺少本地成功记录而直接重做。 |
| 有稳定引用和观测能力的独立长作业运行超过 30 分钟，Worker 已等待 | 作业不因等待超时而被终止，等待不持续推理或占用 Agent 执行槽位；正常会话结束和工作室服务重启不将其作为会话后台工作清理，满足接续条件后恢复。 |
| 外部作业缺少稳定引用或必要观测能力 | 明确说明不可自动观测，保留已知信息和接续条件；不把暂时未知当成失败或自动重新提交。 |
| Assistant、Leader、Worker 共用的额度池耗尽 | 无须再次调用该池即可记录状态并发送基本通知；合并受影响工作的恢复检查，按可靠信号或允许的低频探测接续，无法检查时显示“等待恢复确认”。 |
| 用户已授权一项宿主支持且范围明确的动作，例如删除选定算例的结果并保留输入文件 | Guard 依据已有授权直接放行，由执行方完成动作，无须用户再次逐字批准命令；实际效果限制在约定范围内，输入文件保留，且能查到授权依据与执行结果。 |
| Guard 审查超时或暂时不可用，尚未形成审查结果 | 不执行待审动作，也不视为已作出授权拒绝；服务恢复后可在当前有效指令和授权下继续审查，不要求仅因技术故障就提供新证据或重新授权。 |
| Guard 批准后，脚本、目标范围或授权依据变化 | 受影响的旧批准失效，按当前动作版本和有效授权重新核验；这不属于拒绝后的重复申请，同一命令文本也不能沿用旧批准获得新的副作用权限。 |
| Guard 已完成审查并明确拒绝，授权依据和实际效果未变，仅更换命令写法或包装脚本 | 不凭形式变化反复审查同一被拒绝效果；只有新证据或实质性缩小范围才重新审查，无可行方案时说明真正的障碍。 |
| Watchdog 很久未看到进度，但没有确定故障证据 | 区分合理等待和进展疑点，向当前负责人提供证据；不直接判失败、改变方向或启动替代工作。 |
| 纠正或遗忘系统管理的经验条目后，恢复旧会话并读取其来源及可追溯派生记录 | 已失效的旧结论不会重新成为有效记忆或当前指令，也不能被旧 Worker 重新写回；不要求穷尽扫描全部历史自由文本，但当前决定和授权仍以最新有效记录为准，遗忘长期偏好本身不等于撤销任务授权。 |
| Worker 读取负责人指定的共享事实和其他 Worker 的成果 | 允许用于自己的任务；新增任务、改变共同约定或要求他人执行，仍经负责人安排。 |
| 用户跨渠道说“继续那个任务” | 能唯一定位就继续原任务；多个合理候选且会影响实质动作时才询问，不因换入口重复建任务。 |

## 暂缓选择与范围排除

下列事项已经讨论，但没有在当前基线中固定为具体实现承诺：

| 事项 | 当前结论 |
| --- | --- |
| 具体模型清单、排序和角色边界 | 允许组合、默认选择、升级条件和实际边界由用户配置；选择规则按[选择与调整](#选择与调整)，保留前文已表达的 Advisor 偏好和模型限制。 |
| 使用 DeepSeek 作为 Assistant | 可选方案，尚未选定，也不能代替不依赖模型的基本通知路径。 |
| 各类失败的具体恢复动作 | 额度恢复后的自动接续按[额度耗尽](#额度耗尽)约定；其他恢复动作随任务和后续指令决定，不固定统一重跑或修改参数矩阵。 |
| 并发数、检查周期和记忆实现 | 属于可调配置或实现细节，本文不承诺具体数值；额度恢复探测是否允许及其间隔按[额度耗尽](#额度耗尽)配置。 |
| 首批真实试用任务 | 按需要由用户选择，不作为整理需求或开始设计的前置条件；具备最小可用能力后，可以进行自愿试用。 |
| 纯 Router 与简单任务委派 | 当前保留所有业务任务委派的分工；可根据实际使用重新评估简短、无外部操作任务的委派成本，但未获用户明确调整前，不自行放宽 Assistant 的职责。 |
| Worker 直接澄清事实 | 首版保留经负责人转达的通信边界；实际出现大量事实澄清转述时，再由用户决定是否允许指定 Worker 在既定任务内有限交流，不预先建设横向通信协议，也不下放派工或修改共同约定的权限。 |
| 微信 | 后续渠道目标；首版入口为 DSH GUI 和飞书。 |
| 独立交付 Reviewer | 暂缓，不恢复为强制关卡。 |
| 自定义费用预测、日／任务支出上限、预算驱动降级 | 当前不做；额度停止与恢复按[额度耗尽](#额度耗尽)约定。 |
| 计算与执行环境基础设施 | 不建设或管理本地、SSH、cx05、Slurm 执行后端；宿主动作约束、沙箱能力接入和长作业生命周期协调仍在范围内，受[原型差异与设计前提](#原型差异与设计前提)约束。 |
| 群聊或多用户协作 | 当前不要求，不为首版建设复杂群组权限系统。 |
| 每项执行或机制都有永久 Bot | 不要求。避免固定部门、强制完整花名册，以及独立的长作业或维护角色。 |

此前推演了普通调查、明确立项的项目，以及长作业结束后继续处理等场景。它们用于说明上述要求，不是实际立项指令，也不要求现在执行这些任务。

本文没有选定存储引擎、配置格式、队列协议、界面布局、执行后端或实施里程碑。后续实现选择不能被表述成用户此前已经确认的需求。
